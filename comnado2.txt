### 1. Reparar PDM definitivamente (El eslabón perdido)

En tus pruebas anteriores, `pdm run` fallaba con `ModuleNotFoundError: No module named 'asyncpg'` porque cuando desactivaste el entorno virtual (`use_venv false`), PDM creó una carpeta vacía llamada `__pypackages__`, y cuando usaste `.venv`, ese entorno virtual se creó sin el módulo `pip` adentro (`No module named pip`).

Tienes **dos formas** de dejarlo 100% operativo hoy:

* **Opción A — Reparar el `.venv` de PDM offline (Para que `pdm run` funcione tal como dice el Runbook):**
Ejecuta estos 3 comandos en CMD dentro del proyecto para inyectar `pip` de forma nativa (con `ensurepip`, que ya viene incluido en Python sin requerir internet) e instalar tus paquetes en el `.venv`:
```cmd
cd /d E:\sri\soluciones\DG\VisorDG\app\backend

:: 1. Reactivar el uso de .venv en PDM y borrar la carpeta vacía __pypackages__
pdm config python.use_venv true
if exist __pypackages__ rmdir /s /q __pypackages__

:: 2. Inyectar pip dentro del .venv de forma 100% offline usando el módulo nativo ensurepip
E:\sri\soluciones\DG\VisorDG\app\backend\.venv\Scripts\python.exe -m ensurepip --upgrade

:: 3. Instalar tus 65 wheels dentro del .venv
E:\sri\soluciones\DG\VisorDG\app\backend\.venv\Scripts\python.exe -m pip install --no-index --find-links=E:\sri\soluciones\DG\offline -r requirimientos.txt

```


*Cómo verificar si funcionó:* Ejecuta `pdm run verificar`. Verás que PDM ya reconoce `asyncpg`, `pandas` y `fastapi` sin arrojar `ModuleNotFoundError`.


* **Opción B — Usar el Python global directo (Si prefieres no depender de PDM):**
Como ya instalaste todo en `E:\py\python.exe`, puedes reemplazar cualquier comando `pdm run ...` del manual por:


* Cargar todo: `E:\py\python.exe cargas.py todo --origen local`

* Refrescar: `E:\py\python.exe cargas.py refrescar`

* Verificar: `E:\py\python.exe cargas.py verificar`

### 4. Desbloquear el Acceso desde Otras Computadoras / Otras Redes

Para resolver tanto el `Connection Refused` (puerto 4443 caído) como el `ERR_CONNECTION_TIMED_OUT` (puerto 9000 bloqueado hacia otras PCs):

* **Idea 1: Abrir el Firewall de Windows 11 en el servidor (Obligatorio)**
Ejecuta en CMD como **Administrador** dentro del servidor (`10.2.0.17`):


```cmd
netsh advfirewall firewall add rule name="SRI_VisorDG_9000" dir=in action=allow protocol=TCP localport=9000 profile=any
netsh advfirewall firewall add rule name="SRI_HTTPS_443" dir=in action=allow protocol=TCP localport=443 profile=any

```


*Verificación:* Prueba entrar a `[http://10.2.0.17:9000](http://10.2.0.17:9000)` desde otra PC de tu misma red.


* **Idea 2: Cambiar el Perfil de Red de Windows 11 de "Público" a "Privado"**
En Windows 11, si la red figura como `Public`, el sistema aplica bloqueos estrictos adicionales. En PowerShell como Administrador:
```powershell
Get-NetConnectionProfile
# Si NetworkCategory dice "Public", cámbialo a "Private":
Set-NetConnectionProfile -InterfaceIndex (Get-NetConnectionProfile).InterfaceIndex -NetworkCategory Private

```


*Verificación:* Corre `Get-NetConnectionProfile` de nuevo y confirma que `NetworkCategory` diga `Private` (o `DomainAuthenticated`).
* **Idea 3: Unificar el VisorDG en el puerto 443 (Plan Maestro si el SRI bloquea el puerto 9000 entre subredes)**
Si desde otra red del SRI el puerto `9000` sigue dando *Timed Out* porque los switches institucionales solo dejan pasar el puerto `443` (HTTPS), **evita pedir permisos de firewall de red** publicando el VisorDG en el puerto `443` (o si no vas a usar la app vieja de Flask en este servidor, pon el VisorDG como página principal del puerto `443`).


* **Si NO usas Flask en este servidor nuevo:** En el bloque `server { listen 443 ssl http2; ... }` de tu `nginx.conf`, reemplaza los `location` de `flask_backend` por los dos `location` (`/` y `/api/`) que tienes en el puerto `9000` (apuntando a `visordg_backend` y quitando la línea `Content-Security-Policy` restrictiva de la línea 91 para que permita WebSockets y estilos del visor).


* *Verificación:* Al entrar a `[https://10.2.0.17](https://10.2.0.17)` desde cualquier red del SRI, abrirá directamente el VisorDG sin usar el puerto 9000 ni dar error `10061` de Flask.




* **Idea 4: Si SÍ necesitas levantar Flask (Servidor 1 en puerto 4443)**
Si en ese mismo servidor también debe correr la aplicación de retenciones/papeles de trabajo (Flask), busca en qué puerto levantó o iníciala en el `4443`:


```cmd
:: Ver todos los procesos de Python y sus puertos actuales
for /f "tokens=2" %i in ('tasklist /fi "imagename eq python.exe" /nh') do @netstat -ano | findstr %i

```


*Verificación:* Si ves que Flask levantó en el `5000`, cambia `server 127.0.0.1:4443;` por `server 127.0.0.1:5000;` en la línea 68 de `nginx.conf` y ejecuta `nginx -s reload`.
