III. Usuarios y Grupos del Proyecto

3.1 Usuario python (usuario de aplicación)

El proyecto se ejecuta con el usuario python, que debe pertenecer al grupo wheel para usar sudo. Si no cumple lo siguiente, pase al punto 3.2:

⏭️ Si ya existe el usuario python con grupo wheel y puede ejecutar sudo -l sin error, salte a la sección 3.3.

3.2 Creación del usuario python (solo si no existe)

Normalmente se crea durante la instalación del SO. Si no existe, créelo con el usuario administrador (con sudo):

# 1. Crear usuario local python sudo useradd -m -d /home/python -s /bin/bash python sudo passwd python # 2. Incluirlo en wheel para sudo sudo usermod -aG wheel python # 3. Otorgar lectura/escritura sobre /datos sudo mkdir -p /datos sudo chown python:python /datos sudo chmod 755 /datos # 4. Verificar id python sudo -l -U python

3.3 Creación del usuario oracle (propietario de los binarios)

El Oracle Client 21c se descomprime como propiedad del usuario oracle por estandarización. El usuario oracle no requiere sudo ni se usa para conectarse a la base: su única función es ser dueño de los binarios. El usuario python accede a ellos mediante permisos de lectura (ver sección 7.4).

sudo useradd -m -d /home/oracle -s /bin/bash oracle sudo passwd oracle id oracle # Esperado: uid=XXXX(oracle) gid=XXXX(oracle) groups=XXXX(oracle)
⏭️ Si ya existe el usuario oracle (verifíquelo con id oracle), salte a la sección IV.
Nota sobre oinstall. El estándar contempla un grupo oinstall. En la práctica no es necesario para que el ETL funcione: lo que python necesita es leer los binarios y librerías del cliente, lo cual se resuelve con permisos o+rX (sección 7.4). Si su política institucional exige oinstall, créelo y agregue ambos usuarios; de lo contrario, puede omitirlo.

V. Configuración del Sistema Base

5.1 Sincronización de hora (chronyd)

⏭️ Verificación previa. Si systemctl is-active chronyd responde active, salte a la sección 5.2. La sincronización NTP plena (Leap status: Normal) es deseable pero NO obligatoria para el ETL: en servidores de producción aislados chronyd puede no alcanzar ninguna fuente NTP, y eso no impide el funcionamiento mientras la hora del sistema sea correcta.

Con el usuario python. El servicio chronyd debe estar activo y, en lo posible, sincronizado para evitar errores de certificados y de acceso a los repos suscritos:

sudo systemctl enable --now chronyd sudo chronyc -a makestep chronyc tracking # Deseable: "Leap status: Normal" # Si aparece "506 Cannot talk to daemon": sudo dnf install -y chrony sudo systemctl enable --now chronyd sudo chronyc -a makestep
En producción puede aparecer The system clock is skewed... 5.0 seconds with the entitlement server. Es la misma causa: sincronice con chronyc -a makestep para no afectar el acceso a los repos suscritos.

5.2 Actualización del sistema

sudo dnf update -y

5.3 Instalación de paquetes esenciales

⏭️ Verificación previa. Si rpm -q gcc-c++ make openssl-devel libffi-devel los devuelve todos instalados (sin not installed), salte a la sección 5.4.

Necesarios para el cliente Oracle, Spark y la compilación de Python. En producción (sin internet) este comando SÍ funciona contra los repos RHEL suscritos:

VI. Instalación de OpenJDK 21

⏭️ Verificación previa. Si java -version ya devuelve openjdk version "21..." y existe /usr/lib/jvm/java-21-openjdk, salte a la sección VII.

VII. Instalación del Oracle Client 21c Home

⏭️ Verificación previa. Si sqlplus -v devuelve Release 21.x y sqlplus /@STAR_BI_DWH conecta sin pedir contraseña, el cliente y el wallet ya están listos: salte al capítulo VIII (Spark). Esta sección instala el cliente; el wallet y las credenciales se detallan en el Manual 3.
⚠️ NO usar Instant Client 21c — no incluye orapki, mkstore ni tnsping. Use el Oracle Client Home 21c completo: LINUX.X64_213000_client_home.zip (más de 800 MB, binarios 21.3 / 21.15.0.0.0).
📍 Usuarios de esta sección: los pasos 7.1 y 7.4 se ejecutan con python + sudo. Los pasos 7.2 y 7.3 (descompresión y variables del cliente) con el usuario oracle. El cliente image-based no usa instalador gráfico: instalar = descomprimir.

7.1 Preparar directorios (usuario python, con sudo)

sudo mkdir -p /opt/oracle sudo chown oracle:oracle /opt/oracle sudo chmod 755 /opt/oracle # Copiar el instalador (de la carpeta compartida institucional o del portal Oracle) sudo cp /ruta/de/origen/LINUX.X64_213000_client_home.zip /opt/oracle/ sudo chown oracle:oracle /opt/oracle/LINUX.X64_213000_client_home.zip

7.2 Descomprimir el cliente (usuario oracle)

sudo su - oracle cd /opt/oracle unzip -q LINUX.X64_213000_client_home.zip -d client_home # Verificar que el Client Home trae las herramientas: ls /opt/oracle/client_home/bin/sqlplus ls /opt/oracle/client_home/bin/orapki ls /opt/oracle/client_home/bin/mkstore ls /opt/oracle/client_home/bin/tnsping # Los 4 deben existir

7.3 Variables de entorno del usuario oracle

Aún como oracle, editar ~/.bash_profile y agregar:

export ORACLE_HOME=/opt/oracle/client_home export TNS_ADMIN=/opt/oracle/client_home/network/admin export LD_LIBRARY_PATH=/opt/oracle/client_home/lib:$LD_LIBRARY_PATH export PATH=/opt/oracle/client_home/bin:$PATH source ~/.bash_profile exit # regresa a la sesión del usuario python

7.4 Permisos de lectura para python y delegación de directorios (usuario python, con sudo)

Tras descomprimir, muchos archivos (incluidos los .jar de jlib) quedan con permisos 640/750, sin lectura para "otros". Como python no es oracle, no puede leer las librerías y orapki/mkstore fallan con Could not find or load main class oracle.security.pki.... Hay que dar lectura explícita:

# Dar lectura/acceso a "otros" sobre librerías, Java y PKI del cliente sudo chmod -R o+rX /opt/oracle/client_home/lib sudo chmod -R o+rX /opt/oracle/client_home/jlib sudo chmod -R o+rX /opt/oracle/client_home/jdk sudo chmod -R o+rX /opt/oracle/client_home/network/admin # Verificar que python (como "otros") SÍ puede leer el .jar de PKI cat /opt/oracle/client_home/jlib/oraclepki.jar > /dev/null && echo "OK: python lee jlib" || echo "ERROR: sin lectura" # Delegar a python los directorios que el ETL gestiona en runtime: sudo mkdir -p /opt/oracle/client_home/network/admin sudo chown -R python:python /opt/oracle/client_home/network/admin # Directorio de wallets sudo mkdir -p /opt/oracle/wallets sudo chown python:python /opt/oracle/wallets sudo chmod 755 /opt/oracle/wallets
La R mayúscula en o+rX da lectura a archivos y acceso (ejecución) a directorios, sin volver ejecutables los archivos que no lo eran. Es lo correcto para librerías.

7.5 Variables de entorno del usuario python

cat << 'EOF' >> /home/python/.bashrc # === Oracle Client 21c --- Datos Abiertos Facturación === export ORACLE_HOME=/opt/oracle/client_home export ORACLE_WALLET_PATH=/opt/oracle/wallets export TNS_ADMIN="${ORACLE_HOME}/network/admin" export LD_LIBRARY_PATH="${ORACLE_HOME}/lib:${LD_LIBRARY_PATH}" export PATH="${ORACLE_HOME}/bin:${PATH}" # JAVA_HOME para orapki/mkstore: usa el JDK INTERNO del cliente (no el OpenJDK del sistema) export JAVA_HOME="${ORACLE_HOME}/jdk" export PATH="${JAVA_HOME}/bin:${PATH}" # ================================================ EOF source /home/python/.bashrc
⚠️ Conflicto de JAVA_HOME con Spark. El bloque anterior deja JAVA_HOME apuntando al JDK 1.8 interno del cliente (lo que necesitan orapki/mkstore). Spark necesita Java 21. Por eso el servicio systemd de Spark (sección VIII) define su propio JAVA_HOME=/usr/lib/jvm/java-21-openjdk dentro de la unidad, de forma aislada. No dependa del .bashrc para Spark.

7.6 Verificación final (usuario python)

sqlplus -v # Esperado: SQL*Plus: Release 21.0.0.0.0 - Production / Version 21.x which orapki && which mkstore && which tnsping ls -la ${ORACLE_HOME}/lib/libclntsh.so.21.1 ls -la ${ORACLE_HOME}/lib/libnnz21.so # Prueba decisiva: orapki debe arrancar (imprime versión, no error de clase) orapki wallet create -wallet /opt/oracle/wallets -auto_login 2>&1 | head -3
Si orapki imprime su versión y pide contraseña, la infraestructura del cliente está lista. El wallet y las credenciales (STAR_BI_DWH + SRIDW) se crean en el Manual 3.

VIII. Instalación de Apache Spark 4.0.2 y Servicio Spark Connect

📍 Todo lo referente a Spark vive en este manual. El proyecto Datos Abiertos usa Spark Connect (servidor gRPC en el puerto 15002) para ejecutar consultas masivas a Oracle. Esta sección instala Spark en /opt/spark y crea el servicio systemd que lo mantiene corriendo.
⏭️ Verificación previa — si Spark ya está corriendo, salte esta sección. Compruebe:
sudo systemctl is-active sri-datos-abiertos-spark # Esperado: active timeout 2 bash -c "echo >/dev/tcp/localhost/15002" && echo "PUERTO 15002 OK" ls -ld /opt/spark/spark402 # Debe existir, python:python

Si el servicio está active y el puerto responde, Spark ya está configurado: continúe con la sección IX (correo).

8.1 Preparar directorio de Spark

sudo mkdir -p /opt/spark sudo chown python:python /opt/spark sudo chmod 755 /opt/spark

8.2 Obtener el binario de Spark 4.0.2

# DESARROLLO (con internet): cd /opt/spark wget https://archive.apache.org/dist/spark/spark-4.0.2/spark-4.0.2-bin-hadoop3.tgz
📍 PRODUCCIÓN (sin internet): copie previamente el archivo a /home/python/offline/spark-4.0.2-bin-hadoop3.tgz (vía SCP / repositorio interno) y continúe desde la descompresión.

8.3 Descomprimir y normalizar la ruta a spark402

cd /opt/spark # Desde internet (dev) o desde el archivo offline (prod): tar xzf spark-4.0.2-bin-hadoop3.tgz # o: tar xzf /home/python/offline/spark-4.0.2-bin-hadoop3.tgz mv spark-4.0.2-bin-hadoop3 spark402 ls /opt/spark/spark402/bin/spark-submit # Debe existir sudo chown -R python:python /opt/spark

8.4 Copiar el driver JDBC de Oracle a Spark

Spark necesita el driver ojdbc11.jar (y los JAR de PKI para leer el wallet) en su carpeta jars/:

cp $ORACLE_HOME/lib/ojdbc11.jar /opt/spark/spark402/jars/ cp $ORACLE_HOME/lib/oraclepki.jar /opt/spark/spark402/jars/ 2>/dev/null cp $ORACLE_HOME/lib/osdt_core.jar /opt/spark/spark402/jars/ 2>/dev/null cp $ORACLE_HOME/lib/osdt_cert.jar /opt/spark/spark402/jars/ 2>/dev/null ls -la /opt/spark/spark402/jars/ojdbc11.jar # Confirmar
Si ojdbc11.jar no está en $ORACLE_HOME/lib, descárguelo de la web de Oracle (versión compatible con 21c) y colóquelo en /opt/spark/spark402/jars/. El servicio lo referencia con --jars.

8.5 Crear el servicio systemd sri-datos-abiertos-spark

Crear el archivo /etc/systemd/system/sri-datos-abiertos-spark.service (con sudo vim):

[Unit] Description=SRI Datos Abiertos Facturacion - Spark Connect Server After=network.target [Service] Type=simple User=python Group=python Environment="JAVA_HOME=/usr/lib/jvm/java-21-openjdk" Environment="SPARK_HOME=/opt/spark/spark402" Environment="ORACLE_HOME=/opt/oracle/client_home" Environment="TNS_ADMIN=/opt/oracle/wallets" Environment="LD_LIBRARY_PATH=/opt/oracle/client_home/lib" Environment="PYSPARK_PYTHON=/home/python/sri_datos_abiertos_facturacion/venv/bin/python" WorkingDirectory=/opt/spark/spark402 ExecStart=/opt/spark/spark402/bin/spark-submit \ --packages org.apache.spark:spark-connect_2.13:4.0.2 \ --jars /opt/spark/spark402/jars/ojdbc11.jar \ --conf spark.connect.grpc.binding.port=15002 \ --conf spark.connect.grpc.binding.address=0.0.0.0 \ --conf spark.driver.memory=10g \ --conf spark.executor.memory=10g \ --conf spark.driver.extraJavaOptions="-Doracle.net.tns_admin=/opt/oracle/wallets -Doracle.net.wallet_location=/opt/oracle/wallets" \ --conf spark.executor.extraJavaOptions="-Doracle.net.tns_admin=/opt/oracle/wallets -Doracle.net.wallet_location=/opt/oracle/wallets" \ --class org.apache.spark.sql.connect.service.SparkConnectServer \ internal Restart=on-failure RestartSec=10 TimeoutStartSec=120 [Install] WantedBy=multi-user.target
⚠️ Nombre único del servicio: sri-datos-abiertos-spark.service. El archivo de unidad, los comandos systemctl y los journalctl deben usar siempre este nombre. Si una instalación previa dejó otro nombre (p.ej. sri-spark-connect), deshabilítelo antes para no tener dos servidores compitiendo por el puerto 15002.

8.6 Habilitar y arrancar el servicio

sudo systemctl daemon-reload sudo systemctl enable sri-datos-abiertos-spark.service sudo systemctl start sri-datos-abiertos-spark.service # El primer arranque descarga el paquete spark-connect_2.13 (en dev). En prod sin internet, # ese paquete debe estar precargado en el repositorio local de ivy/maven del usuario python. sleep 20 sudo systemctl status sri-datos-abiertos-spark.service --no-pager # Esperado: active (running)

8.7 Verificar que Spark Connect responde

timeout 2 bash -c "echo >/dev/tcp/localhost/15002" && echo "PUERTO 15002 OK" # Ver logs en vivo si algo falla: sudo journalctl -u sri-datos-abiertos-spark.service -f
📍 Producción sin internet y --packages. El parámetro --packages org.apache.spark:spark-connect_2.13:4.0.2 intenta resolver desde internet en el primer arranque. En producción, ese JAR debe estar precargado en /home/python/.ivy2 o reemplazado por la ruta local del JAR en --jars. Coordine con QA/Desarrollo para incluir el paquete de Spark Connect en el material offline.

IX. Conexión de Correo (SMTP)

📍 El ETL envía una notificación por correo al finalizar cada corrida (estado del proceso). Esta sección valida la conectividad mínima al servidor SMTP. La configuración fina (remitente, destinatarios) vive en configlnx.toml.
⏭️ Si el correo ya funciona (el ETL envía notificaciones sin error), salte esta sección.

9.1 Verificar conectividad al puerto SMTP

# Prueba mínima: que el servidor alcance el puerto 25 (o 587) del SMTP institucional timeout 3 bash -c "echo >/dev/tcp/<HOST_SMTP>/25" && echo "SMTP 25 OK" || echo "SMTP 25 NO alcanzable" # Alternativa con net-tools/telnet si está disponible: curl -v telnet://<HOST_SMTP>:25 2>&1 | head -5

9.2 Prueba de envío básico con Python

Prueba mínima que el ETL replica internamente (sin autenticación, puerto 25; ajustar si su SMTP exige TLS/587):

python3.13 - << 'PYEOF' import smtplib from email.mime.text import MIMEText host = "SMTP_HOST"; port = 25 msg = MIMEText("Prueba de correo Datos Abiertos - infraestructura OK") msg["Subject"] = "[Datos Abiertos] Prueba SMTP" msg["From"] = "datos_abiertos@sri.gob.ec" msg["To"] = "destinatario@sri.gob.ec" with smtplib.SMTP(host, port, timeout=10) as s: s.sendmail(msg["From"], [msg["To"]], msg.as_string()) print("Correo enviado OK") PYEOF
Si el SMTP institucional exige TLS y autenticación, use el puerto 587 con s.starttls() y s.login(user, pass). Lo mínimo que debe funcionar es la conectividad del paso 9.1.

X. Instalación Offline de Librerías Python (/opt/librerias)

📍 Producción sin internet. Todas las dependencias Python (wheels) se copian a /opt/librerias y se instalan sin acceso a PyPI. El directorio debe existir y ser propiedad de python:python para instalar sin sudo.

10.1 Crear el directorio con permisos correctos

# Crear si no existe; debe ser de python para instalar sin sudo sudo mkdir -p /opt/librerias sudo chown python:python /opt/librerias sudo chmod 755 /opt/librerias ls -ld /opt/librerias # Esperado: drwxr-xr-x python python

10.2 Colocar los wheels y validar instalación offline

# Copiar los .whl traídos desde una máquina con internet a /opt/librerias ls -la /opt/librerias/ # pandas, numpy, oracledb, pyspark, pyinstaller, toml, pydantic ... # Instalación offline dentro del venv del proyecto (sin internet): source /home/python/sri_datos_abiertos_facturacion/venv/bin/activate pip install --no-index --find-links=/opt/librerias -r \ /home/python/sri_datos_abiertos_facturacion/requirements.txt deactivate
El instalador datos_abiertos.bash (Manual 5) usa esta misma carpeta cuando detecta ausencia de internet. Mantener /opt/librerias actualizado con los wheels que liste requirements.txt.
