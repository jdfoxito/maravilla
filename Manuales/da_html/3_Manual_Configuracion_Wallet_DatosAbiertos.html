Configuración de Wallets Oracle

Datos Abiertos Facturación — RHEL 10.x · Oracle Client 21c · Dos credenciales: STAR_BI_DWH + SRIDW

ResumenCrear y configurar el wallet Oracle con autologin para conexión segura sin exponer contraseñas. Este proyecto usa dos bases: STAR_BI_DWH (idéntica a Trazabilidad) y la nueva SRIDW.
AlcanceInstalación del cliente (resumen autocontenido), TNS para ambas bases, creación de las dos credenciales en un mismo wallet y validación con SQL*Plus y Python.
Orden de ejecuciónManual 3 de 5: 1) Infraestructura → 2) Python 3.13.5 → 3) Wallet Oracle → 4) Usuarios SSH → 5) Despliegue
Usuario de ejecuciónLocal python. No se usa root ni oracle para ejecutar.
VariablesORACLE_HOME=/opt/oracle/client_home · ORACLE_WALLET_PATH=/opt/oracle/wallets
ServidorProducción 10.2.2.218 (sriapp44)

Si TODAS las líneas imprimen [OK], el wallet ya tiene las dos credenciales: puede saltar directamente al Manual 4 (Usuarios SSH). Si solo conecta STAR_BI_DWH, vaya directo a la sección IV-bis (agregar SRIDW). Si nada conecta, recorra el manual desde la sección que indique cada [FALTA].
# VERIFICACIÓN RÁPIDA DEL WALLET - Datos Abiertos # Ejecutar como usuario python. Cada línea reporta [OK] o [FALTA]. # [Sec. 0.2] Variables de entorno Oracle [ -n "$ORACLE_HOME" ] && [ -n "$TNS_ADMIN" ] && echo "[OK] variables Oracle" || echo "[FALTA] -> Seccion 0.2" # [Sec. V] Conexión real sin contraseña a las DOS bases (validación decisiva) sqlplus -s /@STAR_BI_DWH <<< "exit" >/dev/null 2>&1 && echo "[OK] conecta STAR_BI_DWH" || echo "[FALTA] -> Seccion V / III (tnsnames STAR)" sqlplus -s /@SRIDW <<< "exit" >/dev/null 2>&1 && echo "[OK] conecta SRIDW" || echo "[FALTA] -> Seccion IV-bis / 3.2 (tnsnames SRIDW)"
La validación decisiva es la conexión real con sqlplus /@ALIAS (sección V): si ambas conectan sin pedir contraseña, el autologin funciona para las dos bases del proyecto.

0.1 Usuario de Ejecución y Prerrequisitos

📍 Todo este manual lo ejecuta el usuario python. No se usa root ni oracle para ejecutar. Conexión: SSH con usuario institucional → sudo su - python → verificar con whoami.

0.1.1 Verificar usuario y permisos

whoami # Esperado: python id python # Debe incluir el grupo wheel (para sudo) sudo -l # El usuario debe poder ejecutar con sudo id oracle # Debe existir; se crea en el Manual 1 (solo dueño de binarios)

0.2 Variables de entorno

⏭️ Verificación previa. Si echo $ORACLE_HOME y echo $TNS_ADMIN ya devuelven sus rutas y echo $JAVA_HOME apunta a ${ORACLE_HOME}/jdk, salte a la sección I (o directo a la II si el cliente está sano).
# 1) ¿Están definidas? echo $ORACLE_HOME # /opt/oracle/client_home echo $TNS_ADMIN # /opt/oracle/client_home/network/admin echo $LD_LIBRARY_PATH | grep oracle # 2) Si NO están, agregarlas al .bashrc del usuario python: cat << 'EOF' >> /home/python/.bashrc # === Oracle Client 21c --- Datos Abiertos Facturación === export ORACLE_HOME=/opt/oracle/client_home export ORACLE_WALLET_PATH=/opt/oracle/wallets export TNS_ADMIN="${ORACLE_HOME}/network/admin" export LD_LIBRARY_PATH="${ORACLE_HOME}/lib:${LD_LIBRARY_PATH}" export PATH="${ORACLE_HOME}/bin:${PATH}" # JAVA_HOME: requerido por orapki y mkstore (son scripts Java) export JAVA_HOME="${ORACLE_HOME}/jdk" export PATH="${JAVA_HOME}/bin:${PATH}" # ================================================ EOF source /home/python/.bashrc
⚠️ El JAVA_HOME es obligatorio para el wallet. Las herramientas orapki y mkstore son scripts Java. Sin JAVA_HOME apuntando al JDK del cliente (${ORACLE_HOME}/jdk), fallan con Could not find or load main class oracle.security.pki... (ver Solución de Problemas).

I. Cuándo Borrar el Cliente Oracle y Empezar de Nuevo

⏭️ Solo si aplica. Esta sección y la II son para reinstalar el cliente. Si sqlplus -v ya devuelve Release 21.x y el cliente está sano, salte a la sección III (TNS).

Si la configuración del Oracle Client no funciona (no conecta por wallet, errores persistentes de librerías, instalación a medias o de origen dudoso), se borra el cliente y se instala desde cero.

1.1 Respaldar lo que funciona, de pronto sea necesario

BK=/home/python/oracle_backup_$(date +%Y%m%d_%H%M%S) mkdir -p "$BK" cp /opt/oracle/client_home/network/admin/sqlnet.ora "$BK"/ 2>/dev/null cp /opt/oracle/client_home/network/admin/tnsnames.ora "$BK"/ 2>/dev/null cp -rp /opt/oracle/wallets "$BK"/wallets_copia grep -r -i oracle_home /etc/profile.d/ /etc/profile 2>/dev/null > "$BK"/origen_variables.txt echo "Respaldo en: $BK"; ls -la "$BK"

1.2 Eliminar el cliente previo (los wallets quedan intactos)

ls -al /opt/oracle/ sudo rm -rf /opt/oracle/client_home ls -la /opt/oracle/wallets/ # Confirmar que wallets sigue presente

II. Descompresión e Instalación del Oracle Client 21c

⏭️ Si sqlplus -v ya devuelve Release 21.x y el cliente está sano, salte a la sección III (TNS).

2.1 Ubicar el instalador

ls -al /opt/oracle/LINUX.X64_213000_client_home.zip # Esperado: ~880 MB

2.2 Descomprimir en el directorio destino

sudo mkdir -p /opt/oracle/client_home sudo unzip -q /opt/oracle/LINUX.X64_213000_client_home.zip -d /opt/oracle/client_home ls /opt/oracle/client_home/ ls /opt/oracle/client_home/bin/sqlplus

2.3 Asignar propietario y permisos

sudo chown -R oracle:oracle /opt/oracle/client_home # Dar lectura al usuario python sobre librerías, Java y PKI: sudo chmod -R o+rX /opt/oracle/client_home/lib sudo chmod -R o+rX /opt/oracle/client_home/jlib sudo chmod -R o+rX /opt/oracle/client_home/jdk sudo chmod -R o+rX /opt/oracle/client_home/network/admin cat /opt/oracle/client_home/jlib/oraclepki.jar > /dev/null && echo "OK: python lee jlib" || echo "ERROR: sin lectura"
Al hacer chown -R oracle:oracle, muchos .jar vienen con permisos 640/750 (sin lectura para "otros"). Como python no es oracle, no puede leer oraclepki.jar y orapki falla. El chmod -R o+rX lo resuelve. El wallet puede ser python:python; no necesita oinstall.

2.4 Verificar versión y componentes del wallet

sqlplus -v which orapki && which mkstore && which tnsping ls -la ${ORACLE_HOME}/jdk/bin/java ls -la ${ORACLE_HOME}/jlib/oraclepki.jar

III. Configuración de SQLNET.ORA y TNSNAMES.ORA

📍 Contexto de ejecución: siga como python (verifique con whoami). Párese en el directorio de red de Oracle:
cd /opt/oracle/client_home/network/admin pwd # Confirmar: /opt/oracle/client_home/network/admin

3.1 Colocar los archivos .ora y darlos al usuario python

# Crear vacíos y darlos a python (luego pega el contenido) sudo touch ${TNS_ADMIN}/sqlnet.ora ${TNS_ADMIN}/tnsnames.ora sudo chown python:python ${TNS_ADMIN}/sqlnet.ora ${TNS_ADMIN}/tnsnames.ora sudo chmod 644 ${TNS_ADMIN}/sqlnet.ora ${TNS_ADMIN}/tnsnames.ora ls -la ${TNS_ADMIN}/

Contenido del sqlnet.ora (editar sin sudo)

vim ${TNS_ADMIN}/sqlnet.ora # sqlnet.ora — autenticación por wallet NAMES.DIRECTORY_PATH= (TNSNAMES, EZCONNECT) WALLET_LOCATION = (SOURCE = (METHOD = FILE) (METHOD_DATA = (DIRECTORY = /opt/oracle/wallets)) ) SQLNET.WALLET_OVERRIDE = TRUE SSL_CLIENT_AUTHENTICATION = FALSE SSL_VERSION = 0
Si aparece ORA-12638: credential retrieval failed, agregue SQLNET.AUTHENTICATION_SERVICES= (NONE) al sqlnet.ora. Con NONE, Oracle usa exclusivamente el wallet.

3.2 Editar tnsnames.ora — DOS bases: STAR_BI_DWH y SRIDW

vim ${TNS_ADMIN}/tnsnames.ora

El alias STAR_BI_DWH coincide exactamente con el del wallet y con configlnx.toml. Use el bloque correspondiente a su ambiente; el alias se mantiene igual en los tres, lo que cambia es el HOST.

STAR_BI_DWH — Desarrollo (10.12.4.94)

STAR_BI_DWH = (DESCRIPTION= (ADDRESS= (PROTOCOL=TCP) (HOST=sri33) (PORT=1521) ) (CONNECT_DATA= (SERVER=dedicated) (SERVICE_NAME=STAR) ) )

STAR_BI_DWH — Preproducción / Test (10.12.5.204)

STAR_BI_DWH = (DESCRIPTION= (ADDRESS= (PROTOCOL=TCP) (HOST=10.12.3.95) (PORT=1521) ) (CONNECT_DATA= (SERVER=dedicated) (SERVICE_NAME=star) ) )

STAR_BI_DWH — Producción (10.2.2.218)

STAR_BI_DWH = (DESCRIPTION= (ADDRESS= (PROTOCOL=TCP) (HOST=sri28) (PORT=1521) ) (CONNECT_DATA= (INSTANCE_NAME=star) (SERVER=dedicated) (SERVICE_NAME=STAR) ) )
Confirme HOST y SERVICE_NAME con el DBA. En producción el host suele ser sri23v / sri22v (o el SCAN correspondiente) en lugar de sri33 (desarrollo).

SRIDW — segunda base (agregar el bloque del ambiente correspondiente)

En el mismo tnsnames.ora, agregar el bloque de SRIDW según el ambiente:

# --- Desarrollo --- SRIDW= (DESCRIPTION= (ADDRESS= (PROTOCOL=TCP) (HOST=10.12.4.10) (PORT=1523) ) (CONNECT_DATA= (INSTANCE_NAME=SRIDW) (SERVER=dedicated) (SERVICE_NAME=SRIDW) ) ) # --- Test --- SRIDW= (DESCRIPTION= (ADDRESS= (PROTOCOL=TCP) (HOST=10.12.3.71) (PORT=1521) ) (CONNECT_DATA= (SERVER=dedicated) (SERVICE_NAME=SRIDW) ) ) # --- Producción --- SRIDW= (DESCRIPTION = (ADDRESS_LIST = (ADDRESS = (PROTOCOL = TCP)(HOST = sridw-scan.sri.ad)(PORT = 1521)) ) (CONNECT_DATA = (SERVICE_NAME = sridw) ) )
⚠️ Un solo bloque SRIDW por archivo. Use únicamente el bloque del ambiente en el que está trabajando. No deje los tres bloques SRIDW= simultáneamente en el mismo tnsnames.ora: Oracle tomaría el primero y podría conectar al ambiente equivocado.

3.3 Validar resolución TNS de ambas bases

tnsping STAR_BI_DWH; echo "exit code: $?" tnsping SRIDW; echo "exit code: $?"
📍 RHEL 10: tnsping puede no imprimir nada y eso es NORMAL (glibc 2.39). Si echo $? devuelve 0, la resolución funciona. La validación real es con sqlplus /@ALIAS (sección V).

IV. Wallet con Autologin — Cinco Escenarios

📍 Contexto: usuario python (verifique con whoami). Los comandos orapki y mkstore usan la ruta completa del wallet (-wrl /opt/oracle/wallets), así que puede ejecutarlos desde cualquier directorio. No necesita sudo salvo para crear el directorio del wallet la primera vez.

Orden de preferencia: crear desde cero (A) → usar el existente (B) → restaurar de respaldo (C) → traer del sriapp36 (D). Para sumar un alias a un wallet que ya funciona, ver el Escenario E.

Regla transversal. Si restaura un wallet (C o D) y no funciona (Invalid padding, sigue pidiendo contraseña, o el listado falla), no insista: cree el wallet desde cero (A). Es la opción más predecible.

4.0 Pre-chequeo obligatorio: Java para orapki/mkstore

# 1) JDK del cliente existe y JAVA_HOME apunta a él ls -la ${ORACLE_HOME}/jdk/bin/java echo "JAVA_HOME=$JAVA_HOME" # 2) python PUEDE LEER los .jar de PKI (causa #1 de fallo) cat ${ORACLE_HOME}/jlib/oraclepki.jar > /dev/null && echo "OK: lee jlib" || echo "ERROR: sin lectura -> chmod (2.3)" # 3) Si JAVA_HOME está vacío, exportarlo export JAVA_HOME=${ORACLE_HOME}/jdk export PATH=${JAVA_HOME}/bin:${PATH} # 4) Prueba: debe imprimir versión, no error de clase orapki wallet create -wallet /opt/oracle/wallets -auto_login -pwd [clave] 2>&1 | head -3

Escenario A — Crear el wallet desde cero (recomendado)

# 1) Directorio del wallet sudo rm -rf /opt/oracle/wallets/ sudo mkdir -p /opt/oracle/wallets sudo chown python:python /opt/oracle/wallets sudo chmod 755 /opt/oracle/wallets # 2) Crear wallet con autologin PORTABLE (genera ewallet.p12 + cwallet.sso) orapki wallet create -wallet /opt/oracle/wallets -auto_login # Solicita contraseña para el wallet. Guárdela en gestor seguro. # 3) Agregar las DOS credenciales: alias esquema clave (las provee el DBA) mkstore -wrl /opt/oracle/wallets -createCredential STAR_BI_DWH BI_DWH [CLAVE_STAR] mkstore -wrl /opt/oracle/wallets -createCredential SRIDW [ESQUEMA_SRIDW] [CLAVE_SRIDW] # 4) Verificar que aparezcan AMBAS mkstore -wrl /opt/oracle/wallets -listCredential
El -listCredential debe mostrar las dos: STAR_BI_DWH y SRIDW. Se usa -auto_login (no -auto_login_local) para que el wallet sea portable.

Escenario B — El wallet ya existe en el servidor

ls -la /opt/oracle/wallets/ # Esperado: cwallet.sso + ewallet.p12 (python:python, 600) mkstore -wrl /opt/oracle/wallets -listCredential

Si lista las credenciales correctamente, no toque nada y pase a validar (sección V). Para agregar SRIDW a un wallet que solo tiene STAR_BI_DWH, vea la sección IV-bis.

Escenario C — Restaurar de un respaldo propio

sudo cp /home/python/oracle_backup_AAAAMMDD_HHMMSS/wallets_copia/* /opt/oracle/wallets/ sudo chown python:python /opt/oracle/wallets/* sudo chmod 600 /opt/oracle/wallets/cwallet.sso /opt/oracle/wallets/ewallet.p12 mkstore -wrl /opt/oracle/wallets -listCredential
Si falla (Invalid padding o sigue pidiendo contraseña): el respaldo está dañado o el cwallet.sso era local al servidor de origen. Vaya al Escenario A.

Escenario D — Traer el wallet del sriapp36

Solo el ewallet.p12 es portable. Tráigalo y regenere el cwallet.sso en este servidor:

sudo cp [ruta]/ewallet.p12 /opt/oracle/wallets/ sudo chown python:python /opt/oracle/wallets/ewallet.p12 sudo chmod 600 /opt/oracle/wallets/ewallet.p12 orapki wallet create -wallet /opt/oracle/wallets -auto_login # regenera cwallet.sso local mkstore -wrl /opt/oracle/wallets -listCredential

Escenario E — Agregar un alias nuevo a un wallet existente

vim ${TNS_ADMIN}/tnsnames.ora # 1) agregar el bloque del nuevo alias mkstore -wrl /opt/oracle/wallets -createCredential NUEVO_ALIAS ESQUEMA [CLAVE] # 2) credencial mkstore -wrl /opt/oracle/wallets -listCredential # 3) verificar y probar tnsping NUEVO_ALIAS sqlplus /@NUEVO_ALIAS

IV-bis. Agregar la Credencial SRIDW a un Wallet que ya Tiene STAR_BI_DWH

📍 Caso típico de este proyecto: el wallet de Trazabilidad ya existe con STAR_BI_DWH y solo falta sumar SRIDW. No hay que recrear nada: son dos pasos.

Paso 1 — Agregar el bloque SRIDW al tnsnames.ora

vim ${TNS_ADMIN}/tnsnames.ora # Pegar el bloque SRIDW del ambiente correspondiente (ver sección 3.2) tnsping SRIDW; echo "exit code: $?"

Paso 2 — Agregar la credencial SRIDW al wallet existente

mkstore -wrl /opt/oracle/wallets -createCredential SRIDW [ESQUEMA_SRIDW] [CLAVE_SRIDW] # Pide la contraseña del wallet (la que se definió al crearlo) mkstore -wrl /opt/oracle/wallets -listCredential # Debe listar AHORA: STAR_BI_DWH y SRIDW

Paso 3 — Validar SRIDW

sqlplus /@SRIDW # Conexión exitosa = entra sin pedir contraseña

V. Validación de Conexión

5.1 Prueba con SQL*Plus (sin contraseña) — ambas bases

sqlplus /@STAR_BI_DWH # Connected to: ... SQL> (sin pedir contraseña) sqlplus /@SRIDW # Connected to: ... SQL> (sin pedir contraseña)
Si ambas conectan sin pedir contraseña, el autologin del wallet funciona para las dos bases del proyecto.

5.2 Prueba con Python (oracledb, instalación OFFLINE) — ambas bases

📍 Producción sin internet: traiga el wheel cp313 / manylinux x86_64 de oracledb a /opt/librerias e instálelo offline. Como el ETL usa modo Thick (init_oracle_client()), no hace falta cryptography; con --no-deps funciona.
# Instalar offline en el venv del proyecto source /home/python/sri_datos_abiertos_facturacion/venv/bin/activate pip install --no-index --no-deps --find-links=/opt/librerias oracledb python3 -c "import oracledb; print('oracledb', oracledb.version)" # Probar conexión por wallet a las DOS bases python3.13 - << 'PYEOF' import oracledb, os os.environ['TNS_ADMIN'] = '/opt/oracle/client_home/network/admin' os.environ['ORACLE_HOME'] = '/opt/oracle/client_home' oracledb.init_oracle_client() for alias in ('STAR_BI_DWH', 'SRIDW'): with oracledb.connect(dsn=alias) as con, con.cursor() as cur: cur.execute("SELECT 1 FROM dual") print(f"OK {alias}:", cur.fetchone()) PYEOF deactivate
