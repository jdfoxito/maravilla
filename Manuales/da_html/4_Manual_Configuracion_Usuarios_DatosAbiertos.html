0. Verificación Rápida — Paso a Paso

✅ Atajo. Si la copia entre servidores ya fue configurada antes, ejecute como usuario python en 10.2.2.218 el bloque siguiente. Si TODAS las líneas imprimen [OK], la conexión y la escritura remota ya están configuradas: puede saltar directamente al Manual 5 (Despliegue). Si alguna imprime [FALTA], vaya únicamente a la sección indicada entre corchetes.
# === VERIFICACIÓN RÁPIDA DE COPIA SSH - Datos Abiertos === # Ejecutar como usuario python EN 10.2.2.218. Cada línea reporta [OK] o [FALTA]. KEY="/home/python/.ssh/sri_datos_abiertos_key" REMOTE_PATH="/opt/rh/jbcs-httpd24/root/var/www/html/descargas/downloads/datosAbiertosFacturacion" # [Sec. 0/II] Llave privada ed25519 presente y con permisos 600 [ -f "$KEY" ] && [ "$(stat -c '%a' "$KEY" 2>/dev/null)" = "600" ] && echo "[OK] llave SSH local" || echo "[FALTA] -> Seccion II (ssh-keygen)" # [Sec. III/IV] Conexión SSH por llave a Quito (sin password, timeout corto) ssh -i "$KEY" -o BatchMode=yes -o ConnectTimeout=8 datos_abiertos@10.1.15.11 "echo ok" >/dev/null 2>&1 \ && echo "[OK] conecta Quito 10.1.15.11" || echo "[FALTA] -> Seccion III (authorized_keys Quito)" # [Sec. III/IV] Conexión SSH por llave a Guayaquil ssh -i "$KEY" -o BatchMode=yes -o ConnectTimeout=8 datos_abiertos@10.11.0.15 "echo ok" >/dev/null 2>&1 \ && echo "[OK] conecta Guayaquil 10.11.0.15" || echo "[FALTA] -> Seccion III (authorized_keys Guayaquil)" # [Sec. I/IV] Escritura efectiva en la ruta remota de Quito (prueba real y limpieza) ssh -i "$KEY" -o BatchMode=yes -o ConnectTimeout=8 datos_abiertos@10.1.15.11 \ "touch $REMOTE_PATH/.probe_$$ && rm -f $REMOTE_PATH/.probe_$$" >/dev/null 2>&1 \ && echo "[OK] escritura remota Quito" || echo "[FALTA] -> Seccion I (permisos REMOTE_PATH)"
Este bloque solo puede comprobar lo verificable desde el servidor python: la llave local, la conexión por llave y la escritura efectiva en el remoto. La creación del usuario datos_abiertos y del directorio de descargas (secciones I y III) ocurre en los servidores remotos como root; si la conexión o la escritura fallan, esas secciones son el lugar a revisar.

0.1 Verificación del Usuario python en el Servidor de Ingeniería de Datos

📍 Antes de generar llaves, confirme en 10.2.2.218 que trabaja como python y que ~/.ssh existe con permisos correctos (sin esto, ssh-keygen y ssh fallan).
whoami # Esperado: python id python # grupo python (+ wheel para sudo) # Crear ~/.ssh si no existe (sin sudo, es del propio usuario) mkdir -p /home/python/.ssh chmod 700 /home/python/.ssh ls -ld /home/python/.ssh # Esperado: drwx------ python python

I. Configuración en Servidores de Descargas (10.1.15.11 y 10.11.0.15)

📍 Ejecutar como root (o sudo) en CADA servidor de descargas. Repita las tres subsecciones en Quito y en Guayaquil.
⏭️ Verificación previa (en cada remoto, como root). Si id datos_abiertos ya existe y la ruta de descarga tiene permiso de escritura para ese usuario (compruébelo con su - datos_abiertos -c "touch $REMOTE_PATH/.t && rm $REMOTE_PATH/.t && echo OK"), salte a la sección II.

1.1 Crear usuario del sistema operativo (como root o sudo)

useradd datos_abiertos passwd datos_abiertos # Establecer contraseña si es requerido

1.2 Crear directorio .ssh con permisos seguros

mkdir -p /home/datos_abiertos/.ssh chmod 700 /home/datos_abiertos/.ssh chown datos_abiertos:datos_abiertos /home/datos_abiertos/.ssh

1.3 Verificar/crear ruta de descarga con permisos de escritura

# Ruta esperada por el script datos_abiertos.bash: REMOTE_PATH="/opt/rh/jbcs-httpd24/root/var/www/html/descargas/downloads/datosAbiertosFacturacion" # Crear si no existe, con permisos para el usuario datos_abiertos mkdir -p "$REMOTE_PATH" chmod 775 "$REMOTE_PATH" chown datos_abiertos:datos_abiertos "$REMOTE_PATH" # Validar que datos_abiertos puede escribir (sin sudo): su - datos_abiertos -c "touch $REMOTE_PATH/test_write && rm $REMOTE_PATH/test_write && echo 'PERMISOS OK'"

II. Configuración en Servidor de Producción 10.2.2.218 (usuario python)

⏭️ Verificación previa. Si ls -l /home/python/.ssh/sri_datos_abiertos_key ya existe (con permisos 600), la llave ya está generada: salte a la sección III (o a la 2.3 si solo falta distribuir la pública).

2.1 Generar llave SSH ed25519

ssh-keygen -t ed25519 -f /home/python/.ssh/sri_datos_abiertos_key -N ""
  • No usar passphrase (el -N "" la deja vacía).
  • Nombre sugerido: sri_datos_abiertos_key (ajustar a estándares de Infraestructura).
  • El usuario ejecutor es python, no root.

2.2 Extraer llave pública para distribución

cat /home/python/.ssh/sri_datos_abiertos_key.pub > /tmp/public_key.txt

2.3 Copiar llave pública a servidores remotos

scp /tmp/public_key.txt root@10.1.15.11:/tmp/ scp /tmp/public_key.txt root@10.11.0.15:/tmp/
Alternativa. Si scp no está disponible, usar WinSCP, un cliente SFTP gráfico o rsync.

III. Autorización en Servidores Remotos (como root)

📍 Ejecutar como root en CADA servidor de descargas (Quito y Guayaquil).
⏭️ Verificación previa (en cada remoto). Si grep -qF "$(cat /tmp/public_key.txt)" /home/datos_abiertos/.ssh/authorized_keys no devuelve error (la pública ya está autorizada), salte a la sección IV.

3.1 Agregar la llave pública en cada servidor de descargas

cat /tmp/public_key.txt >> /home/datos_abiertos/.ssh/authorized_keys chmod 600 /home/datos_abiertos/.ssh/authorized_keys chown -R datos_abiertos:datos_abiertos /home/datos_abiertos/.ssh

3.2 Configurar SSH para permitir autenticación por llave

En /etc/ssh/sshd_config verificar:

PubkeyAuthentication yes AuthorizedKeysFile .ssh/authorized_keys # Reiniciar el servicio SSH solo si se modificó el archivo: systemctl restart sshd
En RHEL 10 ambas directivas (PubkeyAuthentication yes y AuthorizedKeysFile .ssh/authorized_keys) ya son el valor por defecto del servidor OpenSSH; normalmente no hay que tocar nada. Revise también que no haya una directiva Match o un archivo en /etc/ssh/sshd_config.d/ que las sobrescriba. Valide la sintaxis antes de reiniciar con sshd -t.

IV. Validación de Conectividad (usuario python)

4.1 Probar conexión SSH

ssh -i /home/python/.ssh/sri_datos_abiertos_key datos_abiertos@10.1.15.11 "echo 'Conexión Quito OK'" ssh -i /home/python/.ssh/sri_datos_abiertos_key datos_abiertos@10.11.0.15 "echo 'Conexión Guayaquil OK'"

4.2 Probar escritura en ruta remota (simulando la operación del script)

⚠️ Corrección. El manual previo tenía los scp partidos con \ seguido de espacio, lo que rompía el comando al copiar. A continuación, comandos en una sola línea con variables, listos para pegar.
# Definir variables una vez para no repetir rutas largas: KEY="/home/python/.ssh/sri_datos_abiertos_key" REMOTE_PATH="/opt/rh/jbcs-httpd24/root/var/www/html/descargas/downloads/datosAbiertosFacturacion" # Crear archivo de prueba local: echo "Prueba $(date)" > /tmp/test_sync_$(date +%Y%m%d).txt # Copiar a ambos servidores (Quito y Guayaquil): scp -i "$KEY" /tmp/test_sync_*.txt datos_abiertos@10.1.15.11:"$REMOTE_PATH/" scp -i "$KEY" /tmp/test_sync_*.txt datos_abiertos@10.11.0.15:"$REMOTE_PATH/"

4.3 Verificar recepción y limpiar

KEY="/home/python/.ssh/sri_datos_abiertos_key" REMOTE_PATH="/opt/rh/jbcs-httpd24/root/var/www/html/descargas/downloads/datosAbiertosFacturacion" # Verificar en remoto: ssh -i "$KEY" datos_abiertos@10.1.15.11 "ls -la $REMOTE_PATH/test_sync_*.txt" # Limpieza post-validación (ambos servidores): ssh -i "$KEY" datos_abiertos@10.1.15.11 "rm $REMOTE_PATH/test_sync_*.txt" ssh -i "$KEY" datos_abiertos@10.11.0.15 "rm $REMOTE_PATH/test_sync_*.txt" rm /tmp/test_sync_*.txt /tmp/public_key.txt

V. Solución de Problemas Comunes

DescripciónSolución
Permission denied (publickey)Revisar permisos de .ssh (700) y authorized_keys (600) en el remoto. Validar que la llave pública esté en authorized_keys y que se usa la llave correcta con -i.
Host key verification failedEjecutar ssh-keygen -R 10.1.15.11, o aceptar el fingerprint en la primera conexión manual.
No route to host / TimeoutValidar conectividad de red (ping, firewall), que el servidor remoto esté encendido y que el puerto 22 esté abierto.
Permission denied al escribir en REMOTE_PATHEn remoto: chmod 775 <ruta> y chown datos_abiertos:datos_abiertos <ruta>. Validar que datos_abiertos es dueño del directorio.
~/.ssh: No such file or directory al generar la llaveCrear el directorio primero: mkdir -p /home/python/.ssh && chmod 700 /home/python/.ssh (sección 0.1).
SELinux bloquea la lectura de authorized_keysEn RHEL, si .ssh se creó por una vía no estándar, restaurar contexto: restorecon -R -v /home/datos_abiertos/.ssh. Revisar ausearch -m avc -ts recent si persiste.
